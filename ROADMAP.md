# План развития Snipbox

> Этот документ описывает назначение Snipbox, текущее состояние проекта и порядок следующих улучшений. Этапы расположены по зависимостям: сначала надёжность команд и данных, затем удобство, каталог и выпуск приложения.

## 1. Зачем нужен Snipbox

**Snipbox — личная библиотека команд для терминала.** Она помогает сохранять полезные команды, быстро находить их, понимать их назначение и повторно использовать без поиска по старым заметкам и истории оболочки.

Пользовательский сценарий простой:

1. Найти команду в поиске или дереве категорий.
2. Прочитать описание и увидеть, для какой системы и оболочки она подходит.
3. Заполнить параметры, например имя ветки или путь к файлу.
4. Просмотреть готовую команду.
5. Скопировать её или явно подтвердить запуск.

Команды хранятся в обычном TOML-файле на компьютере пользователя. Snipbox не требует аккаунта и не отправляет библиотеку в облако. Пользователь сам решает, импортировать ли историю оболочки и настраивать ли синхронизацию через Git.

## 2. Принципы продукта

- **Понятно:** у каждой команды есть имя, описание, категория и примеры параметров.
- **Предсказуемо:** перед запуском пользователь видит, что именно будет выполнено.
- **Локально:** библиотека остаётся на компьютере, пока пользователь сам не настроит синхронизацию.
- **Бережно к данным:** обновление формата и приложения сохраняет пользовательские команды и настройки.
- **По делу:** рабочий список открывается сразу; приветственная информация не перекрывает команды.
- **Кроссплатформенно:** команды отмечаются для подходящей ОС и оболочки, поскольку синтаксис PowerShell и Bash различается.

## 3. Что уже есть

- Go-приложение с терминальным интерфейсом и поисковым ядром на Rust через C ABI.
- Категории, дерево команд, быстрый поиск, панель деталей и меню действий.
- Шаблоны вида `{{branch:feature/new-work}}`, избранное и счётчик использования.
- Локальная библиотека `~/.snipbox/commands.toml` и стартовый набор из 60 команд.
- Импорт истории оболочки, копирование, запуск команд и подтверждение потенциально опасных действий.
- Сборка Windows в один исполняемый файл и инструкции для сборки на других системах.

**Выполнен этап 1:** у стартовых команд появились сведения об оболочках, ОС и нужных утилитах. Эти поля видны в деталях и доступны для редактирования; миграция заполняет их у неизменённых стартовых команд, не перезаписывая пользовательский текст.

Этот список — отправная точка, а не обещание, что каждая функция уже одинаково проверена на всех ОС.

## 4. Очерёдность работ

### Этап 1. Уточнить среду выполнения команды — выполнен

**Зачем:** одна и та же команда может работать в Bash и не работать в PowerShell. Сейчас пользователю важно заранее понимать, где команда применима.

**Что сделать:**

- Добавить к записи необязательные поля оболочки и поддерживаемых платформ.
- Показывать эти сведения в панели деталей и форме редактирования.
- Сохранить совместимость старых TOML-файлов: отсутствие новых полей не должно мешать запуску приложения.
- Помечать команды, которым нужны внешние утилиты, например `dig`, `rg` или `docker`.

**Готово, когда:** для каждой стартовой команды указана подходящая среда, а старые библиотеки открываются без потери данных.

### Этап 2. Сделать запуск понятным и предсказуемым

**Зачем:** пользователь должен знать, какая команда, оболочка и рабочая папка будут использованы.

**Что сделать:**

- Показывать итоговый текст после подстановки переменных до запуска.
- Указывать выбранную оболочку и рабочую папку; дать возможность изменить папку для конкретной команды.
- Показывать код завершения, вывод и понятное сообщение об ошибке.
- Разделить действия «Скопировать» и «Запустить», чтобы случайный Enter не запускал команду.
- Считать использование команды только после успешного копирования или завершившегося запуска.

**Подэтап 2.1 выполнен:** перед обычной командой Snipbox показывает точный текст, текущую оболочку и рабочую папку. Enter запускает команду, Esc отменяет; для опасной команды сохраняется отдельное подтверждение.

**Осталось в этапе 2:** настройка рабочей папки для команды и более подробный результат выполнения с кодом завершения.

**Готово, когда:** перед запуском виден точный текст команды, а после него пользователь понимает, где и с каким результатом она выполнилась.

### Этап 3. Усилить предупреждения и проверку команд

**Зачем:** простое совпадение по слову не объясняет, какие данные затронет команда. Предупреждение должно помогать оценить действие.

**Что сделать:**

- Добавить к командам уровень риска и короткое объяснение последствий.
- Перед выполнением показывать заполненные параметры и предупреждение рядом с итоговой командой.
- Проверять опасные операции для конкретных платформ и оболочек, не полагаясь только на список отдельных слов.
- Для удаления или перезаписи требовать отдельное подтверждение.
- Прямо объяснить в справке, что подтверждение не является песочницей и не ограничивает права процесса.

**Готово, когда:** пользователь видит причину предупреждения и может отменить действие до запуска. Команда не стартует автоматически после заполнения параметров.

### Этап 4. Надёжно управлять библиотекой

**Зачем:** библиотека становится ценнее по мере накопления личных команд; её нельзя случайно перезаписать или потерять при обновлении.

**Что сделать:**

- Проверять обязательные поля и шаблоны при создании и редактировании.
- Показывать найденный дубликат до сохранения новой записи.
- Добавить экспорт и импорт с предварительным просмотром изменений.
- Добавить создание резервной копии и понятное восстановление.
- Сохранять атомарную запись TOML и проверять миграции на старых и пользовательских данных.

**Готово, когда:** ошибки формы объясняются рядом с полем, импорт не заменяет библиотеку молча, а резервную копию можно восстановить по инструкции.

### Этап 5. Ускорить поиск и навигацию

**Зачем:** при большой библиотеке важно быстро сузить результаты и не терять выбранную команду.

**Что сделать:**

- Добавить фильтры по избранному, тегам, оболочке и платформе.
- Сохранить подсветку совпадений и позицию выбранной команды при переключении категорий.
- Сделать ясными пустые состояния: нет результатов, нет записей в категории, команда недоступна в текущей среде.
- Проверить прокрутку длинных списков и деталей на узких и низких терминалах.
- Показывать дерево, панель деталей и меню действий без наложения при изменении размера окна.

**Готово, когда:** ключевые действия доступны с клавиатуры, мышь не запускает команду случайно, а содержимое не выходит за границы терминала.

### Этап 6. Поддерживать качественный каталог

**Зачем:** большое число непонятных или неподходящих команд не делает библиотеку полезнее.

**Что сделать:**

- Развивать разделы Git, PowerShell, Docker, Linux/Bash и Network.
- Для каждой записи указывать задачу, важные флаги, ограничения и безопасные значения параметров.
- Маркировать платформу, оболочку и необходимые внешние программы.
- Удалять дубликаты и проверять примеры на соответствующей системе.
- Поддерживать пользовательские категории и теги без ломки существующего TOML.

**Готово, когда:** каждую стартовую команду можно объяснить одной ясной задачей и пользователь знает, что нужно для её запуска.

### Этап 7. Сделать локальную синхронизацию надёжной

**Зачем:** Git-синхронизация полезна для переноса личной библиотеки, но должна быть прозрачной и не уничтожать локальные правки.

**Что сделать:**

- Перед синхронизацией показывать, какой каталог и удалённый репозиторий будут использованы.
- Проверять незакоммиченные изменения и доступность remote.
- Обрабатывать конфликты с понятной инструкцией, сохраняя локальную копию.
- Сообщать результат отдельно для commit и push.
- Оставить синхронизацию явным действием пользователя.

**Готово, когда:** приложение не делает force push, не скрывает конфликт и не сообщает об успешной отправке, если push завершился ошибкой.

### Этап 8. Подготовить выпуск для пользователей

**Зачем:** готовая программа должна собираться и запускаться на системах, которые указаны в документации.

**Что сделать:**

- Автоматически собирать и проверять Windows, Linux и macOS в CI.
- Публиковать отдельный исполняемый файл для каждой платформы и архитектуры.
- Документировать требования к Go, Rust, cgo и системному линкеру.
- Указать особенности статической линковки: полностью статический исполняемый файл доступен не на каждой ОС.
- Добавить версию, заметки к выпуску и контрольные суммы артефактов.

**Готово, когда:** чистая сборка из инструкции проходит на каждой заявленной платформе, а пользователь может определить, какой файл ему скачать.

## 5. Ближайшие задачи

Рекомендуемый следующий рабочий цикл:

1. Добавить метаданные оболочки и платформы к командам, сохранив чтение старого TOML.
2. Встроить просмотр итоговой команды и выбор рабочей папки перед запуском.
3. Пересмотреть предупреждения и тесты выполнения отдельно для Windows и Unix-подобных систем.
4. Добавить резервную копию и предварительный просмотр импорта.
5. После этого расширять фильтры, каталог и автоматические сборки.

Такой порядок сначала укрепляет безопасность и доверие к данным, а затем увеличивает возможности библиотеки.

## 6. Общие критерии готовности

Любое изменение считается готовым, если:

- пользовательский интерфейс остаётся на английском языке, а ошибки объясняют, что произошло и что делать дальше;
- старые пользовательские записи не удаляются при миграции;
- команда не выполняется без явного действия пользователя;
- тесты покрывают изменённое поведение, а проверки Go и Rust проходят;
- размер терминала и длинные команды не ломают рамки и навигацию;
- документация описывает реальное поведение, ограничения и способ запуска.
